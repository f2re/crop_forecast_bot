# Аудит Crop Forecast Bot — 2026-07-10

## Исходное состояние

До модернизации проект не имел единого надёжного runtime:

- production запускал legacy `run_bot.py` на `pyTelegramBotAPI`;
- aiogram-entrypoint подключал только RAG-router;
- одновременно существовали `handlers.py` и пакет `handlers/`;
- пользовательское состояние хранилось в глобальных словарях;
- Open-Meteo имел несовместимые async/sync контракты;
- scheduler вызывал CRUD без DB session и ожидал другой frost DTO;
- схема создавалась через `create_all()` без миграций;
- ГДД короткого окна назывались сезонными, а ГТК рассчитывался по недостаточному периоду;
- отсутствовали воспроизводимые install/update/rollback и service lifecycle.

Исходное состояние классифицировалось как **непригодное для надёжной production-эксплуатации**.

## Закрытые критические дефекты

| Область | Реализованное исправление |
|---|---|
| Telegram runtime | один aiogram 3.x entrypoint и Router/FSM |
| Состояние | PostgreSQL для профиля, Redis для FSM/locks/deduplication |
| Схема БД | обязательный Alembic и проверка head на startup |
| Погодный API | единый async provider contract и typed DTO |
| Scheduler | DB snapshot, distributed lock, persistent notification deduplication |
| Health | systemd readiness, asyncio heartbeat и watchdog |
| Deploy | native Bash install/update/rollback/status без контейнеров |
| Научные подписи | разделение периода, источника и ограничений показателей |

## Реализованные вертикальные срезы

### 1. Единый runtime

- production-entrypoint: `python -m src.bot.main`;
- Telegram framework: только aiogram 3.x;
- удалены legacy telebot entrypoint и обработчики;
- доступны `/start`, `/help`, `/cancel`;
- поле, культура, сезон, отчёт, уведомления и RAG подключены к одному Dispatcher.

### 2. PostgreSQL, Alembic и профиль поля

- baseline `20260710_0001` принимает чистую или legacy-схему `users`;
- migration `20260710_0002` создаёт:
  - `fields` — координаты, имя, timezone, высота и active flag;
  - `crop_seasons` — культура, дата посева/начала сезона, фактическая фаза, источник и confidence;
- существующие координаты и культура переносятся в `Основное поле` и активный сезон;
- legacy-колонки временно сохраняются и dual-write используются на переходном этапе;
- `create_all()` удалён из production startup;
- deploy/update выполняют backup, `alembic upgrade head` и schema-aware preflight.

### 3. Сезонный Telegram-сценарий

- основной путь: **поле → культура → дата сезона → фактическая фаза → отчёт**;
- дата принимается в форматах `ДД.ММ.ГГГГ` и `ГГГГ-ММ-ДД`;
- будущие и явно ошибочные даты отклоняются;
- озимая культура может иметь дату прошлого календарного года;
- фаза выбирается из справочника культуры и сохраняется как наблюдение пользователя;
- автоматическая фаза не выводится до региональной валидации порогов;
- изменение культуры сбрасывает ранее сохранённую фазу.

### 4. Погодный provider layer

- добавлены application port и domain DTO для погодного провайдера;
- Open-Meteo Forecast API предоставляет оперативное прошлое и прогноз;
- при заданной дате сезона Historical Weather API достраивает прошлый ряд реанализом;
- каждая строка маркируется `reanalysis`, `operational_past` или `forecast`;
- coverage metadata содержит requested/actual period, completeness, source и notes;
- overlap объединяется по локальному календарному дню, приоритет имеет оперативный ряд;
- история ограничена 730 сутками для контролируемой нагрузки;
- недоступность реанализа даёт явный degraded report, а не ложную сезонную сумму.

### 5. Агрометеорологические расчёты

- `Tbase` ГДД берётся из единого `crop_catalog`;
- формула ГДД: `max(0, (Tmax + Tmin) / 2 − Tbase)`, `°C·сут`;
- сезонная сумма заявляется только при покрытии даты начала;
- выводятся valid/expected/missing days и missing fraction;
- автоматическая фенофаза отключена: каталог фаз пока является справочным, а не валидированной моделью;
- ГТК требует минимального числа валидных суток с `Tmean > 10°C`;
- ET₀ обозначается как provider variable;
- frost screening принимает crop/phase/elevation как контекст, но не выдаёт общие 2/0°C за пороги повреждения культуры;
- air 2 m и plant/surface temperature явно разделены.

### 6. Scheduler и эксплуатация

- Redis `SET NX EX` leases защищают jobs и уведомления;
- ключи deduplication включают поле;
- daily digest использует активный сезон и фактическую фазу;
- scheduler освобождает DB session до внешнего I/O;
- production управляется hardened `Type=notify` systemd unit;
- watchdog получает heartbeat из asyncio event loop;
- используются `deploy.sh`, `update.sh`, `rollback.sh`, `status.sh`, `help.sh`;
- releases неизменяемы, данные находятся в `/var/lib`, cache — в `/var/cache`, secrets — в `/etc`.

### 7. Контроль качества

Добавлены тесты:

- fresh и legacy Alembic migrations;
- backfill активного поля и сезона;
- repository roundtrip field/crop/season/phase/timezone/elevation;
- parsing даты сезона и IANA timezone;
- Open-Meteo historical payload и merge precedence;
- GDD source/base/coverage/missing fraction;
- season-aware report formatting;
- Redis lease и scheduler reservation semantics;
- native deployment policy и отсутствие контейнерных артефактов.

CI выполняет ruff, compileall, pytest, `bash -n` и shellcheck.

## Оставшиеся риски

1. **Несколько полей.** Схема поддерживает несколько записей, но Telegram UX пока работает с одним активным полем.
2. **Legacy columns.** `users.latitude`, `users.longitude`, `users.selected_crop` остаются на один переходный цикл для dual-write; требуется отдельная cleanup migration после проверки production backfill.
3. **ГТК.** Нужен согласованный сезонный observation/reanalysis ряд и правила непрерывности вегетационного периода; текущий расчёт остаётся ограниченной оценкой окна.
4. **Фенология.** Пороги GDD не валидированы независимо по культурам и регионам; автоматический вывод фазы намеренно отключён.
5. **Заморозки.** Нет crop/phase damage thresholds, surface temperature, terrain correction и ensemble uncertainty.
6. **Integration tests.** Нужны реальные PostgreSQL/Redis, restart FSM, конкурентный scheduler и mocked full HTTP flow.
7. **Clean-host.** Нужна проверка deploy/update/rollback на Debian 12 и Astra Linux.
8. **RAG startup.** ChromaDB/sentence-transformers требуют lazy initialization и optional dependency profile.
9. **Dependency lock.** Требуется `uv.lock`, проверенный на целевых ОС.
10. **Observability.** Нет JSON logs, correlation ID и метрик latency/error/fallback.
11. **Legacy modules.** Старые ERA5/storage/ML-модули требуют reachability audit и удаления либо переноса.

## Решение о готовности

Проект имеет единый native runtime, обязательную схему БД, устойчивый scheduler и работающий сценарий поля/сезона. Научную и эксплуатационную готовность нельзя считать полной до зелёного CI текущего среза, реальных integration tests, clean-host проверки и независимой валидации фенологии/заморозковых порогов.
