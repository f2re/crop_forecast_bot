# Аудит Crop Forecast Bot — 2026-07-10

## Резюме

До модернизации репозиторий не имел единого работоспособного runtime:

- фактический production-entrypoint запускал `run_bot.py` на синхронном `pyTelegramBotAPI`;
- README предписывал `python -m src.bot.main` на aiogram 3.x;
- aiogram-entrypoint подключал только RAG-router, поэтому основной сценарий был недоступен;
- одновременно существовали `src/bot/handlers.py` и каталог `src/bot/handlers/`, что создавало конфликт импорта;
- пользовательское состояние и выбранная культура хранились в глобальных словарях;
- Open-Meteo имел несовместимые контракты: async-функция возвращала tuple, синхронный caller ожидал dict;
- scheduler вызывал CRUD-генераторы без обязательной DB-сессии и ожидал другую структуру результата заморозков;
- проверка работоспособности подтверждала только запуск команды, но не живой event loop;
- схема БД создавалась через `create_all`, миграции Alembic отсутствовали;
- научные подписи смешивали 14-дневный архив с накоплением ГДД с начала сезона и пытались вычислять 30-дневный ГТК по неполному окну;
- отсутствовали воспроизводимые нативные установка, обновление, rollback и service lifecycle.

Состояние до исправлений классифицируется как **непригодное для надёжной production-эксплуатации**.

## Критические дефекты

| Приоритет | Область | Дефект | Последствие |
|---|---|---|---|
| P0 | Runtime | Два Telegram-фреймворка и две точки запуска | Непредсказуемый production-код |
| P0 | Import | `handlers.py` конфликтовал с `handlers/` | aiogram routers могли не импортироваться |
| P0 | Weather API | Coroutine/tuple использовались как синхронный dict | Агроотчёт завершался исключением и fallback |
| P0 | Scheduler | CRUD вызывался без сессии; frost DTO не совпадал | Фоновые алерты фактически не работали |
| P0 | State | Глобальные `user_states` и pending-словари | Потеря прогресса, гонки, невозможность масштабирования |
| P1 | Health | Проверка не контролировала event loop | Зависший процесс мог считаться рабочим |
| P1 | DB lifecycle | Нет ping/dispose, глобальный nullable singleton | Утечки ресурсов и позднее обнаружение ошибок |
| P1 | Scientific | ГДД за 14 суток назывались сезонными; ГТК считался по короткому ряду | Научно некорректные пользовательские выводы |
| P1 | Deploy | Нет воспроизводимого install/update/rollback/systemd | Ручные, ошибкоопасные обновления |
| P2 | Dependencies | Одновременно telebot/aiogram, дубли aiohttp, лишний sync PostgreSQL driver | Конфликты и избыточная установка |
| P2 | Quality | Нет CI и unit-тестов критических контрактов | Регрессии обнаруживаются в production |

## Реализованные вертикальные срезы

### Единый runtime

- production-entrypoint: `python -m src.bot.main`;
- Telegram framework: только aiogram 3.x;
- legacy `run_bot.py`, telebot handlers и синхронный recommendation handler удалены;
- основной сценарий перенесён в `src/bot/handlers/core.py`;
- добавлены команды `/start`, `/help`, `/cancel` и Telegram command menu;
- поле, культура, отчёт, настройки уведомлений и RAG доступны из единого Dispatcher.

### Состояние, миграции и scheduler

- профиль и координаты хранятся в PostgreSQL;
- FSM использует Redis в production и явный memory fallback в development;
- DB session передаётся middleware;
- добавлены `ping()`, rollback при ошибке и штатный `dispose()`;
- добавлен Alembic baseline `20260710_0001`;
- baseline принимает существующую таблицу `users`, ранее созданную через `create_all()`, и добавляет отсутствующие поля;
- `create_all()` удалён из production startup;
- приложение и runtime doctor требуют совпадения текущей ревизии с Alembic head;
- deploy/update всегда выполняют backup и `alembic upgrade head` до preflight;
- scheduler загружает snapshot целей и освобождает DB session до HTTP/Telegram I/O;
- Redis `SET NX EX` leases обеспечивают distributed job lock;
- frost и daily digest имеют token-checked persistent deduplication;
- при ошибке отправки временная reservation снимается, поэтому уведомление можно повторить;
- ключ frost-event стабилизирован по пользователю, дате и уровню риска, а не по плавающей Tmin.

### Провайдер и расчёты

- Open-Meteo имеет один async API и DTO `AgroWeatherData`;
- sync vendor client изолирован через bounded `asyncio.to_thread`;
- ошибки провайдера явные (`OpenMeteoError`), а не `(None, None)`;
- scheduler и RAG переведены на тот же DTO;
- кэш Open-Meteo вынесен в конфигурируемый writable path;
- ГТК не публикуется при недостаточном тёплом периоде;
- ГДД без даты начала сезона обозначаются как сумма за доступный период;
- фенофаза без даты посева не выводится;
- заморозок обозначается как screening по Tmin воздуха 2 м, с локальным временем модели и без фиктивной вероятности.

### Нативная эксплуатация

- production-процесс управляется hardened systemd unit;
- `Type=notify` сообщает готовность только после проверки схемы, запуска scheduler и bot polling;
- systemd watchdog получает heartbeat из asyncio event loop и перезапускает зависший процесс;
- добавлены `deploy.sh`, `update.sh`, `rollback.sh`, `status.sh`, `help.sh` и совместимый `install-systemd.sh`;
- код хранится в неизменяемых release-каталогах, постоянные данные — в `/var/lib`, кэш — в `/var/cache`, секреты — в `/etc`;
- перед deploy/update создаётся PostgreSQL dump;
- еженедельный update timer доступен как явная opt-in функция;
- конфигурация централизована, а production требует PostgreSQL и Redis.

### Контроль качества

- unit-тесты координат, временных ограничений ГТК/ГДД, frost DTO и heartbeat;
- тесты fresh/adopted Alembic baseline;
- тесты memory/Redis lease semantics и scheduler reservation;
- GitHub Actions: ruff, compileall, pytest, `bash -n` и shellcheck;
- CI запрещает возвращение удалённых deployment-артефактов и `create_all()` bootstrap.

## Оставшиеся риски

1. **Сезон и фаза**. В профиле поля отсутствуют дата посева, сезон, фаза и тип технологии. Без них нельзя корректно интерпретировать ГДД и заморозковую уязвимость.
2. **HTC data source**. Open-Meteo `past_days=14` недостаточно для валидного сезонного ГТК. Нужен согласованный ряд наблюдений/реанализа.
3. **ERA5/CDS workflow**. Существующие climate-модули требуют отдельной проверки сигнатур, файлового кэша, timeout и лицензий; они не включены в основной оперативный сценарий.
4. **RAG startup cost**. ChromaDB/sentence-transformers требуют lazy initialization и отдельного optional dependency profile.
5. **Dependency lock**. Стек консолидирован, но требуется `uv.lock` после проверки совместимости на целевых Debian/Astra окружениях.
6. **Integration tests**. Нужны реальные PostgreSQL/Redis tests, FSM restart tests, конкурентный scheduler test и clean-host systemd smoke test.
7. **Migration rollback**. Initial baseline намеренно необратим через `alembic downgrade`; восстановление выполняется из PostgreSQL backup. Следующие миграции должны проектироваться обратно совместимыми.
8. **Observability**. Нет structured JSON logs, correlation ID и метрик latency/error-rate/provider fallback.
9. **Legacy modules**. Неиспользуемые ERA5/storage/ML-модули ещё требуют reachability audit и удаления либо переноса по слоям.

## Решение о готовности

Критические runtime-контракты, схема БД и дедупликация scheduler приведены к единой production-архитектуре. Релиз нельзя считать научно и эксплуатационно завершённым до зелёного CI этого среза, интеграционных тестов PostgreSQL/Redis/API, модели сезона/поля и clean-host проверки deploy/update/rollback.
