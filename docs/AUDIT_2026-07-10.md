# Аудит Crop Forecast Bot — 2026-07-10

## Резюме

До модернизации репозиторий не имел единого работоспособного runtime:

- Docker запускал `run_bot.py` на синхронном `pyTelegramBotAPI`;
- README предписывал `python -m src.bot.main` на aiogram 3.x;
- aiogram-entrypoint подключал только RAG-router, поэтому основной сценарий был недоступен;
- одновременно существовали `src/bot/handlers.py` и каталог `src/bot/handlers/`, что создавало конфликт импорта;
- пользовательское состояние и выбранная культура хранились в глобальных словарях;
- Open-Meteo имел несовместимые контракты: async-функция возвращала tuple, синхронный caller ожидал dict;
- scheduler вызывал CRUD-генераторы без обязательной DB-сессии и ожидал другую структуру результата заморозков;
- healthcheck Docker проверял только успешный выход Python или DNS, а не работоспособность event loop;
- схема БД создавалась через `create_all`, миграции Alembic отсутствовали;
- научные подписи смешивали 14-дневный архив с накоплением ГДД с начала сезона и пытались вычислять 30-дневный ГТК по неполному окну.

Состояние до исправлений классифицируется как **непригодное для надёжной production-эксплуатации**.

## Критические дефекты

| Приоритет | Область | Дефект | Последствие |
|---|---|---|---|
| P0 | Runtime | Два Telegram-фреймворка и две точки запуска | Непредсказуемый production-код |
| P0 | Import | `handlers.py` конфликтовал с `handlers/` | aiogram routers могли не импортироваться |
| P0 | Weather API | Coroutine/tuple использовались как синхронный dict | Агроотчёт завершался исключением и fallback |
| P0 | Scheduler | CRUD вызывался без сессии; frost DTO не совпадал | Фоновые алерты фактически не работали |
| P0 | State | Глобальные `user_states` и pending-словари | Потеря прогресса, гонки, невозможность масштабирования |
| P1 | Health | Фиктивные healthcheck | Оркестратор считал зависший бот здоровым |
| P1 | DB lifecycle | Нет ping/dispose, глобальный nullable singleton | Утечки ресурсов и позднее обнаружение ошибок |
| P1 | Scientific | ГДД за 14 суток назывались сезонными; ГТК считался по короткому ряду | Научно некорректные пользовательские выводы |
| P1 | Deploy | Нет воспроизводимого deploy/update/systemd | Ручные, ошибкоопасные обновления |
| P2 | Dependencies | Одновременно telebot/aiogram, дубли aiohttp, лишний sync PostgreSQL driver | Конфликты и избыточный образ |
| P2 | Quality | Нет CI и unit-тестов критических контрактов | Регрессии обнаруживаются в production |

## Реализованный вертикальный срез

### Единый runtime

- production-entrypoint: `python -m src.bot.main`;
- Telegram framework: только aiogram 3.x;
- legacy `run_bot.py`, telebot handlers и синхронный recommendation handler удалены;
- основной сценарий перенесён в `src/bot/handlers/core.py`:
  - `/start`;
  - просмотр/ввод поля;
  - Telegram location;
  - ручные координаты;
  - выбор культуры;
  - оперативный агроотчёт;
  - настройка ежедневного отчёта;
  - RAG-router сохранён как отдельный сценарий.

### Состояние и БД

- профиль и координаты хранятся в PostgreSQL;
- FSM использует Redis в production и явный memory fallback в development;
- DB session передаётся middleware;
- добавлены `ping()`, rollback при ошибке и штатный `dispose()`;
- scheduler получает session factory через dependency injection.

### Провайдер и расчёты

- Open-Meteo имеет один async API и DTO `AgroWeatherData`;
- sync vendor client изолирован через bounded `asyncio.to_thread`;
- ошибки провайдера явные (`OpenMeteoError`), а не `(None, None)`;
- scheduler и RAG переведены на тот же DTO;
- ГТК не публикуется при недостаточном тёплом периоде;
- ГДД без даты начала сезона обозначаются как сумма за доступный период;
- фенофаза без даты посева не выводится;
- заморозок обозначается как screening по Tmin воздуха 2 м, с локальным временем модели и без фиктивной вероятности.

### Эксплуатация

- Docker запускает aiogram entrypoint от непривилегированного пользователя;
- Compose добавляет PostgreSQL, Redis, persistent volumes и зависимости по healthcheck;
- heartbeat подтверждает, что event loop продолжает выполняться;
- добавлены:
  - `scripts/deploy.sh`;
  - `scripts/update.sh`;
  - `scripts/install-systemd.sh`;
  - `src/ops/doctor.py`;
  - hardened systemd unit template;
- конфигурация централизована и валидируется до запуска;
- `.env.example` синхронизирован с runtime.

### Контроль качества

- unit-тесты координат, временных ограничений ГТК/ГДД, frost DTO и heartbeat;
- GitHub Actions: ruff, compileall, pytest и Docker build.

## Оставшиеся риски

1. **Alembic baseline**. `create_all()` сохранён только как временный bootstrap. До изменения схемы требуется baseline migration и обязательный `alembic upgrade head`.
2. **Persistent alert deduplication**. Дедупликация алертов пока process-local. Следующий срез должен перенести ключи в Redis с atomic `SET NX EX`.
3. **Сезон и фаза**. В профиле поля отсутствуют дата посева, сезон, фаза и тип технологии. Без них нельзя корректно интерпретировать ГДД и заморозковую уязвимость.
4. **HTC data source**. Open-Meteo `past_days=14` недостаточно для валидного ГТК. Для production нужен сезонный ряд наблюдений/реанализа с согласованным периодом.
5. **ERA5/CDS workflow**. Существующие climate-модули требуют отдельной проверки сигнатур, файлового кэша, timeout и лицензий; они не включены в основной оперативный сценарий.
6. **RAG startup cost**. ChromaDB/sentence-transformers могут существенно увеличивать образ и память. Нужны lazy initialization и отдельный optional profile.
7. **Dependency lock**. Стек консолидирован, но требуется сгенерированный `uv.lock` после проверки совместимости на целевых Astra/Debian окружениях.
8. **Integration tests**. Нужны testcontainers PostgreSQL/Redis, FSM restart tests и smoke test Compose с mock Telegram API.
9. **Observability**. Нет Prometheus/OpenTelemetry, structured JSON logs и метрик latency/error-rate/provider fallback.
10. **Legacy modules**. Неиспользуемые ERA5/storage/ML-модули ещё требуют reachability audit и удаления либо переноса по слоям.

## Решение о готовности

Текущий срез переводит проект из состояния с заведомо неработающими runtime-контрактами в состояние, где основной Telegram-путь, scheduler и deployment используют одну архитектуру. Релиз нельзя считать научно и эксплуатационно завершённым до зелёного CI, Alembic baseline, persistent deduplication и интеграционных тестов PostgreSQL/Redis/API.
