# Аудит Crop Forecast Bot — 2026-07-10

## Исходное состояние

До модернизации проект не имел единого надёжного runtime:

- production запускал legacy `pyTelegramBotAPI`;
- aiogram-entrypoint не содержал основного сценария;
- пользовательское состояние хранилось в глобальных словарях;
- Open-Meteo имел несовместимые async/sync контракты;
- scheduler вызывал CRUD без DB session и ожидал другой frost DTO;
- схема создавалась через `create_all()`;
- короткие погодные окна ошибочно интерпретировались как сезонные;
- отсутствовали воспроизводимые install/update/rollback и service lifecycle.

Исходное состояние было непригодно для надёжной production-эксплуатации.

## Закрытые критические дефекты

| Область | Реализованное исправление |
|---|---|
| Telegram runtime | один aiogram 3.x entrypoint и Router/FSM |
| Состояние | PostgreSQL для профиля, Redis для FSM/locks/deduplication |
| Схема БД | Alembic и обязательная проверка head |
| Погодный API | единый async provider contract и typed DTO |
| Scheduler | DB snapshot, distributed lock, persistent deduplication |
| Health | systemd readiness, asyncio heartbeat и watchdog |
| Deploy | native Bash install/update/rollback/status |
| Научные подписи | разделение источников, периода, пропусков и ограничений |

## Реализованные вертикальные срезы

### 1. Единый runtime

- production-entrypoint: `python -m src.bot.main`;
- только aiogram 3.x;
- удалены legacy handlers и entrypoint;
- доступны `/start`, `/help`, `/cancel`;
- поле, культура, сезон, отчёт, уведомления и RAG подключены к одному Dispatcher.

### 2. PostgreSQL и Alembic

- `20260710_0001` — baseline `users` с принятием legacy-схемы;
- `20260710_0002` — `fields` и `crop_seasons`, backfill координат/культуры;
- `20260710_0003` — provenance timezone/elevation и field-level notifications;
- `create_all()` удалён из production startup;
- deploy/update выполняют backup, `alembic upgrade head` и schema-aware preflight;
- приложение не стартует с устаревшей ревизией.

### 3. Несколько полей

Telegram UX и repository поддерживают:

- создание нового поля;
- список полей;
- одно активное поле пользователя;
- безопасное переключение active field;
- переименование;
- обновление координат;
- проверку владения полем;
- независимые культура, дата сезона, фаза и настройки уведомлений;
- сохранение metadata source для timezone и высоты.

Legacy-колонки `users.latitude`, `users.longitude`, `users.selected_crop`, `users.daily_digest` временно используются для dual-write и будут удалены после production verification.

### 4. Погодный provider layer

- application port и domain DTO;
- Forecast API: operational past + forecast;
- Historical Weather API: сезонный реанализ;
- маркировка строк `reanalysis`, `operational_past`, `forecast`;
- coverage metadata и controlled degraded mode;
- merge по локальному дню с приоритетом оперативного ряда;
- history window ограничен 730 сутками.

### 5. Расчётный слой

- `Tbase` ГДД берётся из единого crop catalogue;
- сезонная сумма заявляется только при полном покрытии начала сезона;
- выводятся valid/expected/missing days и missing fraction;
- автоматическая фенофаза отключена до региональной валидации;
- ГТК требует валидного тёплого окна;
- ET₀ явно маркируется как provider variable;
- frost screening принимает crop/phase/elevation как контекст, но не выдаёт общие 2/0°C за damage thresholds.

### 6. Scheduler и уведомления

- Redis `SET NX EX` leases для jobs и notifications;
- deduplication keys включают `field_id`;
- scheduler использует только активное поле пользователя;
- ежедневный отчёт и frost alerts имеют отдельные field-level switches;
- local calendar date берётся из timezone активного поля;
- DB session освобождается до HTTP/Telegram I/O.

### 7. Нативная эксплуатация

- hardened `Type=notify` systemd unit;
- asyncio heartbeat и watchdog;
- `deploy.sh`, `update.sh`, `rollback.sh`, `status.sh`, `help.sh`;
- immutable releases, `/var/lib` для данных, `/var/cache` для caches, `/etc` для secrets;
- PostgreSQL dump перед deploy/update;
- optional update timer.

### 8. Контроль качества

Тестами покрыты:

- fresh/legacy Alembic migrations до revision `0003`;
- backfill поля, сезона и уведомлений;
- preservation provenance существующих timezone/elevation;
- multi-field create/rename/switch/update;
- независимость сезонов и notification settings двух полей;
- ownership и case-insensitive duplicate names;
- date/timezone parsing;
- Open-Meteo history payload и merge precedence;
- GDD coverage/missing fraction;
- Redis lease и scheduler reservation semantics;
- native deployment policy.

CI выполняет ruff, compileall, pytest, `bash -n` и shellcheck.

## Оставшиеся риски

1. **Integration tests.** Нужны реальные PostgreSQL/Redis, restart FSM, конкурентный scheduler и полный mocked HTTP flow.
2. **Clean-host.** Не выполнен автоматизированный deploy/update/rollback smoke на Debian 12 и Astra Linux.
3. **Legacy columns.** Нужна cleanup migration после проверки backfill на production-копии.
4. **ГТК.** Требуется согласованный сезонный observation/reanalysis ряд и строгие правила непрерывности.
5. **Фенология.** Пороговые GDD-таблицы не валидированы независимо по культурам и регионам.
6. **Заморозки.** Нет crop/phase damage thresholds, surface temperature, terrain correction и ensemble uncertainty.
7. **Notification schedule.** Время запуска daily job пока глобальное; timezone поля используется для календарной дедупликации, но не для индивидуального часа доставки.
8. **RAG startup.** Тяжёлые зависимости требуют lazy initialization и optional profile.
9. **Dependency lock.** Нет проверенного `uv.lock` для целевых ОС.
10. **Observability.** Нет JSON logs, correlation ID и метрик latency/error/fallback.
11. **Legacy modules.** Старые ERA5/storage/ML-модули требуют reachability audit.

## Решение о готовности

Основной Telegram-сценарий, схема БД, multi-field profile, scheduler coordination и нативная эксплуатация приведены к единой архитектуре. Срез можно сливать только после зелёного CI. Полная научная и эксплуатационная готовность требует реальных integration tests, clean-host проверки и независимой валидации фенологии/заморозковых порогов.
