# План развития агрометеорологического бота

Дата актуализации: **2026-08-03**.

## Цель

Сделать бот понятным полевым помощником, который:

- показывает только проверяемые расчёты;
- объясняет каждое число простыми словами;
- не подменяет измерения на поле модельными данными;
- не меняет стадию развития без осмотра и подтверждения пользователя;
- работает на слабом сервере без лишних служб и библиотек.

Подробности по отчётам и стадиям: [`REPORT_AND_PHENOLOGY_PLAN.md`](REPORT_AND_PHENOLOGY_PLAN.md).

## Текущий срез — смысл даты и контроль стадии

### Причина

Одна строка «дата посева/начала сезона» недостаточна. Для томата дата посева семян и дата высадки рассады могут отличаться на несколько недель. Без этого нельзя даже осторожно обсуждать ожидаемую стадию.

Также необходимо знать, когда пользователь последний раз осматривал растения и подтверждал стадию.

### Реализовано

К профилю культуры добавлены:

```text
смысл даты:
- посев
- появление всходов
- высадка рассады
- условное начало наблюдений

условия выращивания:
- открытый грунт
- защищённый грунт
- не указано

тип роста томата:
- детерминантный
- индетерминантный
- не указано

дополнительно:
- сорт
- группа скороспелости
- время последнего подтверждения стадии
- примечание к наблюдению
```

После выбора даты бот обязательно спрашивает, что она означает. Существующие записи получают нейтральное значение «условное начало наблюдений»: бот не объявляет старую дату посевом или высадкой без ведома пользователя.

При выборе стадии сохраняется время наблюдения. Пользователь может нажать **«Стадия не изменилась»**, чтобы обновить время осмотра без смены стадии.

### Напоминание о проверке

Если наблюдение давно не подтверждалось, бот пишет:

```text
Стадия подтверждена 24 суток назад.
При осмотре проверьте, не появилась ли следующая стадия: «Плодоношение».
```

Это только календарное напоминание. Интервал напоминания не является биологическим порогом. Бот:

- не присваивает новую стадию;
- не показывает процент вероятности;
- не считает название следующей стадии результатом модели;
- не меняет запись без нажатия пользователя.

### Проверки текущего среза

- миграция новой схемы;
- сохранение смысла даты;
- сохранение условий выращивания;
- сохранение времени подтверждения стадии;
- проверка допустимых стадий для выбранной культуры;
- местный часовой пояс поля;
- сохранение незавершённого ввода после перезапуска Redis;
- сценарий Telegram от даты до отчёта;
- Python 3.10 и 3.11;
- PostgreSQL, Redis, резервная копия и восстановление.

## Следующий приоритет — полевой журнал

Нужны фактические записи пользователя:

```text
- стадия
- цветение
- первая завязь
- первый зрелый плод
- полив
- показание дождемера
- температура своей станции
- повреждение
- заметка
```

Журнал позволит:

- сравнивать модельные осадки с дождемером;
- проверять предупреждения по факту;
- понимать, когда стадия действительно изменилась;
- накапливать данные для будущей проверки подсказки стадии;
- не смешивать наблюдение пользователя и расчёт модели.

## После журнала — проверяемая подсказка стадии томата

Первая область применения:

- томат, выращенный через рассаду;
- открытый грунт;
- известная дата высадки;
- известный тип роста;
- фактически подтверждённая предыдущая стадия.

Подсказка должна учитывать:

- календарный возраст;
- накопленное тепло;
- тепло после последнего осмотра;
- сильную жару и холод;
- допустимый переход только к соседней стадии;
- сортовую и региональную неопределённость.

Результат должен выглядеть так:

```text
Возможно, пора проверить начало плодоношения.
Это подсказка по сроку, а не результат осмотра.

[Стадия не изменилась]
[Выбрать плодоношение]
[Указать другую]
```

До независимой проверки по разным сезонам и районам бот не должен писать «стадия определена» или показывать проценты.

## Что нельзя добавлять как быстрый расчёт

- автоматическую стадию по одному числу накопленного тепла;
- прогноз урожайности без реальной выборки;
- вероятность града только по CAPE;
- норму полива как разность осадков и эталонного испарения;
- дозы препаратов и удобрений без нормативного источника;
- универсальные пороги повреждения для всех сортов и стадий.

## Технический долг

- вынести цикл погодных предупреждений из `scheduler.py` в прикладную службу;
- окончательно разделить крупный `handlers/core.py` на узкие обработчики;
- отделить выбранный профиль культуры от истории сезонов;
- переименовать старое поле `frost_alerts_enabled` в общее поле погодных предупреждений;
- удалить переходные столбцы таблицы пользователей после подтверждённого обновления;
- постепенно включить строгую проверку типов и проверку безопасности;
- измерить память и время расчёта на целевом слабом сервере;
- не вводить очереди и отдельные службы без измеренной необходимости.

## Критерии ближайшего выпуска

- миграция проходит на чистой и существующей базе;
- дата всегда имеет явный смысл;
- время последнего осмотра сохраняется;
- стадия не меняется автоматически;
- напоминание не выдаётся за биологический расчёт;
- основной Telegram-сценарий проходит после перезапуска;
- все автоматические проверки зелёные;
- основная ветка обновляется безопасно и может быть откатана.
