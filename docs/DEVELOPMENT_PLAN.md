# План развития агрометеорологического бота

Дата актуализации: **2026-08-03**.

## Цель

Бот должен быть устойчивым полевым помощником, который:

- показывает только проверяемые расчёты и источники;
- отделяет наблюдение, прогноз, реанализ и климатическую норму;
- объясняет неопределённость простыми словами;
- не выдаёт погодный маркер за факт повреждения, появления вредителя или
  необходимость обработки;
- не повторяет одно и то же предупреждение после каждого запуска модели;
- не теряет важное уточнение из-за суточного ограничения;
- обновляется на целевой системе только из проверенной основной ветки;
- работает на слабом сервере без лишних служб.

## Фактическое состояние

### Архитектура

Подтверждено кодом:

- единственная рабочая точка запуска использует aiogram 3.x;
- PostgreSQL хранит пользователей, поля, сезоны, историю расчётов и постоянное
  состояние уведомлений;
- Redis используется для состояния диалога, распределённых блокировок,
  идемпотентности переходов и суточного ограничения сообщений;
- схема изменяется миграциями Alembic;
- внешние погодные источники скрыты за асинхронными поставщиками;
- запуск и остановка закрывают HTTP-сеансы, базу, Redis, планировщик и Telegram;
- развёртывание выполняется нативными службами systemd;
- рабочий выпуск переключается атомарно и проверяется по heartbeat;
- при неудачном обновлении предусмотрен возврат предыдущего выпуска;
- GitHub может запускать серверный обновлятор ограниченным SSH-ключом, но
  systemd-таймер остаётся основным резервом.

### Пользовательский путь

Работают:

```text
поле
→ одна или несколько культур
→ смысл даты и наблюдаемая стадия
→ агроотчёт
→ погодные условия
→ температура почвы
→ допущенные модели вредителей
→ история и настройки уведомлений
```

### Научные расчёты

Подтверждены отдельными договорами и проверками:

- накопленное тепло культуры от указанной даты;
- накопленные осадки и сухие серии;
- ГТК только на согласованном завершённом периоде;
- сравнение осадков с эталонным испарением без выдачи нормы полива;
- ансамблевый скрининг холода, жары, сильных осадков, порывов ветра и
  конвективной неустойчивости;
- температура модельного слоя почвы 0–7 см;
- ограниченный каталог погодозависимых моделей вредителей.

Не заявляются:

- валидированный прогноз урожайности;
- факт заражения по погоде;
- вероятность ущерба по доле ансамбля;
- автоматическая стадия культуры по одной сумме температур;
- официальный статус опасного явления по одному модельному порогу;
- нормы полива, удобрений или препаратов без полного контекста и нормативного
  источника.

## Завершённый срез: смысловые погодные периоды

### Причина повторов

Погодный расчёт выполняется четыре раза в сутки и может дополнительно запускаться
после перезапуска. Старый ключ защиты включал отдельную дату события и
10-процентную ступень доли ансамбля. Небольшое изменение модельных участников
создавало новый ключ для того же периода жары, дождя или ветра.

### Решение

Период сравнивается по четырём признакам:

```text
тип
+ начало
+ окончание
+ наивысший уровень
```

PostgreSQL хранит последний принятый снимок. Повторное сообщение создаётся только
при новом периоде, изменении границ или уровня, разделении, объединении либо
снятии будущего сигнала. Изменение доли ансамбля, медианы или разброса без смены
периода не создаёт сообщение.

Пользователь видит явное уточнение:

```text
Жара продлится дольше: до 11 августа вместо 9 августа.
```

или:

```text
Ранее ожидавшийся период жары больше не подтверждается.
```

## Завершённый срез: надёжная доставка переходов

Дополнительный аудит выявил, что один Redis-ключ нельзя использовать одновременно
как подтверждение конкретного изменения и как суточный лимит.

Реализовано разделение:

```text
transition:<hash>  — конкретное изменение уже доставлено
daily:<date>       — обычная сводка сегодня уже отправлена
```

Это обеспечивает:

- отсутствие повтора после отправки Telegram и аварии до записи PostgreSQL;
- сохранение другого изменения, подавленного суточным лимитом;
- отправку ожидающего изменения в следующие локальные сутки;
- снятие обеих коротких резерваций при ошибке Telegram;
- отдельный немедленный путь для существенно изменившегося высокого риска;
- явное состояние `deferred` в истории отдельных сигналов.

Все периоды одного типа сохраняются полностью. Ограничение размера сообщения
применяется к типам риска, а не к первым пяти периодам. Недоставленные типы не
поглощаются новым PostgreSQL-снимком.

## Завершённый срез: защита от повторных карточек поля

Погодные риски относятся к координатной точке. Если пользователь случайно создал
несколько карточек с одинаковыми координатами и одинаковой политикой доставки,
они объединяются в один погодный объект:

- один запрос прогноза;
- одно Telegram-сообщение;
- все названия полей и культуры сохраняются в тексте;
- минимальный `field_id` становится владельцем постоянного снимка;
- карточки с разными режимами или тихими часами остаются раздельными;
- ежедневные агроотчёты не объединяются, поскольку зависят от культуры и сезона.

## Завершённый срез: воспроизводимая настройка развёртывания

Основным механизмом остаётся серверный таймер, проверяющий `main` каждые
15 минут. GitHub-сигнал после успешного CI использует отдельный SSH-ключ с
принудительной единственной командой.

Добавлены:

- ручной `workflow_dispatch` для проверки подключения;
- `scripts/configure-github-deploy.sh` для Linux и macOS;
- создание окружения `production` через GitHub CLI;
- запись секретов окружения без вывода их значений;
- запись `DEPLOY_TRIGGER_ENABLED` как переменной репозитория;
- проверка всех созданных имён;
- необязательный тестовый запуск workflow;
- ShellCheck нового скрипта в основном CI.

## Проверки завершённых срезов

Сценарии покрывают:

- изменение доли ансамбля при неизменном периоде;
- продление, сокращение и снятие периода;
- естественное прохождение первого дня;
- повтор того же перехода;
- другой переход в те же сутки;
- повтор на следующие сутки;
- ошибку Telegram и повторную попытку;
- несколько раздельных периодов одного типа;
- очередь типов при искусственном ограничении сообщения;
- восстановление состояния после перезапуска;
- тихие часы и высокий приоритет;
- повторные координаты и разные политики доставки;
- договор GitHub Environment, переменной репозитория и ручного запуска;
- Python 3.10/3.11, PostgreSQL, Redis, миграции, запуск и ShellCheck.

## Следующий вертикальный срез: полевой журнал

Необходимо хранить фактические записи пользователя:

```text
- стадия культуры;
- цветение, завязь и зрелость;
- найденный вид вредителя;
- показание ловушки;
- кладки и возраст личинок;
- доля повреждённых растений или листовой поверхности;
- полив;
- показание дождемера;
- температура своей станции;
- температура почвенного датчика и глубина;
- повреждение;
- заметка и фотография.
```

Журнал нужен для:

- сравнения модельных осадков с дождемером;
- сравнения температуры слоя с датчиком;
- проверки предупреждений по факту;
- определения реальной смены стадии;
- оценки ошибки окон вредителей;
- накопления региональной статистики без подмены наблюдения моделью.

Критерии готовности:

- записи привязаны к полю, культуре и местному времени;
- единицы и глубина измерения обязательны;
- редактирование сохраняет историю;
- фотография не считается автоматическим диагнозом;
- экспорт пригоден для анализа и резервного копирования;
- после перезапуска данные не теряются;
- сценарий доступен из Telegram.

## После журнала

### Местная проверка прогнозов

Для каждого поля накапливать модельный прогноз, срок, фактическое наблюдение,
ошибку температуры и осадков, пропуски, поставщика, сезон и регион. До
достаточной выборки поправки не применяются автоматически.

### Проверка моделей вредителей

Для каждой модели сохранять исходное наблюдение, рассчитанное окно, фактическую
дату стадии, температуру своей станции, регион, сорт или гибрид и число
подтверждений. Проценты появления или ущерба запрещены до независимой проверки
по нескольким сезонам и районам.

### Официальные предупреждения

Добавить отдельный слой CAP от уполномоченных служб. Он не смешивается с
ансамблевым скринингом и сохраняет орган-источник, территорию, начало и окончание,
тяжесть, достоверность, время обновления и отмену или замену сообщения.

## Технический долг

1. Окончательно вынести погодный цикл из `scheduler.py` в прикладную службу.
2. Заменить последовательное обновление состояний отдельных сигналов одной
   транзакцией.
3. Разделить крупный `handlers/core.py` на узкие обработчики.
4. Объединить погодный и вредительский планировщики единым договором задания.
5. Переименовать переходное поле `frost_alerts_enabled` в общее поле погодных
   предупреждений.
6. Удалить переходные столбцы пользователя после подтверждённой миграции всех
   установок.
7. Включить строгую проверку типов для изменённых модулей.
8. Измерить память, время расчёта и задержки на целевой слабой системе.
9. Добавить проверку реального Telegram-сценария после развёртывания.
10. Добавить интерфейс объединения или удаления повторных карточек поля.
11. Не вводить очередь, отдельный сервер или тяжёлую библиотеку без измеренной
    необходимости.

## Риски

### Первое обновление семантической схемы

До миграции старые установки не имеют смыслового снимка. Первый активный период
после обновления может быть отправлен один раз. Это ожидаемая инициализация.

### Повреждение постоянного состояния

Повреждённая запись PostgreSQL обрабатывается с запретом отправки. Бот пишет
ошибку, но не сбрасывает состояние молча и не рассылает все сигналы заново.

### Изменение модели поставщика

Снимок содержит имя модели. При смене модели прежнее состояние не считается
сопоставимым; новый источник может создать одно начальное сообщение.

### Недоступность GitHub

Немедленный сигнал может не сработать из-за сети или SSH. Серверный таймер
остаётся резервом и продолжает проверку.

### Нет доступа к целевой системе из CI

CI проверяет код, миграции и договоры, но не доказывает доступность конкретного
SSH-сервера или Telegram-бота. Для production обязательны ручной
`workflow_dispatch`, проверка журнала обновления и реальный Telegram-сценарий.

## Критерии ближайшего выпуска

- все проверки кода, тесты и миграции зелёные;
- один период жары не повторяется при четырёх расчётах в сутки;
- продление, сокращение и снятие формулируются явно;
- повтор перехода после аварии не отправляется;
- другое изменение в те же сутки не теряется;
- все периоды и недоставленные типы остаются в очереди;
- повторные карточки одной геоточки не создают повторное погодное сообщение;
- перезапуск не сбрасывает снимок;
- тихие часы не теряют отложенное изменение;
- высокий уровень обходит тихие часы только при существенном изменении;
- GitHub-настройка воспроизводится одним скриптом;
- базовый systemd-таймер включён;
- обновление проверяет точный коммит `main`;
- ошибка запуска приводит к возврату предыдущего выпуска;
- основной Telegram-сценарий и ручной GitHub-триггер проверены на реальной
  установке.
