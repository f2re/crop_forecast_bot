# Автообновление и политика погодных уведомлений

Дата аудита: **2026-08-03**.

## 1. Вывод аудита

### Развёртывание

В проекте уже есть безопасное автоматическое обновление целевой системы:

```text
systemd-таймер
→ scripts/update.sh
→ проверка точного коммита main в GitHub Actions
→ новый изолированный выпуск
→ миграции
→ предварительная проверка
→ атомарное переключение
→ проверка работоспособности
→ автоматический откат при ошибке
```

Таймер `crop-forecast-bot-update.timer` проверяет `main` каждые 15 минут. Это
надёжный основной способ: серверу не нужен входящий веб‑перехватчик, открытый
HTTP‑порт или сторонний агент.

Недостаток только один: после успешного коммита обновление может начаться не
сразу. Для ускорения добавлен необязательный процесс
`.github/workflows/deploy-production.yml`. После успешной проверки коммита
`main` он посылает ограниченную SSH-команду целевой системе. Команда запускает
тот же `crop-forecast-bot-update.service`; все проверки, миграции и откат
остаются на стороне сервера.

### Уведомления

Погодная проверка запускается четыре раза в сутки: около 00:10, 06:10, 12:10 и
18:10 по часовому поясу планировщика. Дополнительно после здорового запуска бота
может выполняться стартовая проверка. При нескольких обновлениях программы за
день это увеличивает число перерасчётов.

Прежняя защита от повторов считала отдельными событиями:

```text
тип явления
+ отдельная календарная дата
+ уровень
+ ступень доли ансамбля по 10 процентных пунктов
```

Поэтому один период жары на пять–семь суток получал новый технический отпечаток,
когда очередной запуск модели немного менял долю участников ансамбля. Отображение
уже объединяло соседние дни в один период, но защита от повторов работала раньше
этого объединения. Это и было основной причиной серии однотипных сообщений.

## 2. Новая политика уведомлений

Один непрерывный период описывается только существенными признаками:

```text
тип явления
+ дата начала
+ дата окончания
+ наивысший уровень
```

Повторное сообщение отправляется только в следующих случаях:

1. появился новый будущий период;
2. период начнётся раньше или позже;
3. период закончится раньше или продлится;
4. изменился уровень;
5. период разделился на несколько частей или объединился;
6. ранее ожидавшееся будущее явление больше не подтверждается.

Не считаются новым событием:

- изменение доли ансамбля без смены уровня;
- изменение медианы, квантилей или числа участников;
- поступление нового запуска модели с теми же границами периода;
- естественное завершение уже прошедшего календарного дня;
- перезапуск бота или потеря краткосрочного ключа Redis.

Последний принятый снимок периода хранится в PostgreSQL в таблице
`risk_delivery_states`. Redis остаётся дополнительной защитой от параллельной
отправки и повторной обработки одного перехода.

### Пример

Первое сообщение:

```text
Жара ожидается 5–9 августа.
```

Следующие перерасчёты с тем же периодом не создают сообщений, даже если доля
вариантов изменилась с 55 до 72 процентов.

Уточнение:

```text
Жара продлится дольше: до 11 августа вместо 9 августа.
```

Снятие:

```text
Ранее ожидавшийся период жары 5–9 августа больше не подтверждается.
```

## 3. Базовое автообновление таймером

Первичная установка:

```bash
git clone https://github.com/f2re/crop_forecast_bot.git
cd crop_forecast_bot
sudo bash scripts/deploy.sh
```

Проверка:

```bash
systemctl status crop-forecast-bot.service
systemctl status crop-forecast-bot-update.timer
systemctl list-timers crop-forecast-bot-update.timer
sudo journalctl -u crop-forecast-bot-update.service -n 200 --no-pager
```

Ручной запуск той же безопасной процедуры:

```bash
sudo systemctl start crop-forecast-bot-update.service
sudo journalctl -u crop-forecast-bot-update.service -f
```

Не следует заменять эту процедуру на обычный `git pull` внутри рабочего каталога:
так теряются атомарность, проверка миграций, контроль работоспособности и откат.

## 4. Немедленный сигнал после успешного коммита

Этот режим необязателен. Таймер должен оставаться включённым как резерв.

### 4.1. Создать отдельный ключ

На доверенной административной машине:

```bash
ssh-keygen \
  -t ed25519 \
  -f cropbot_github_deploy \
  -C crop-forecast-bot-github-deploy
```

Закрытый ключ `cropbot_github_deploy` будет секретом GitHub. Открытый ключ
`cropbot_github_deploy.pub` устанавливается на сервер.

### 4.2. Установить ограниченный обработчик на сервере

Из актуального выпуска проекта:

```bash
sudo bash scripts/install-github-deploy-trigger.sh \
  /путь/cropbot_github_deploy.pub
```

Скрипт создаёт отдельного пользователя `cropdeploy` и разрешает этому ключу
только одну операцию:

```text
systemctl --no-block start crop-forecast-bot-update.service
```

Ключ не получает произвольную командную оболочку, псевдотерминал, перенаправление
портов или агент SSH. В `sudoers` разрешена только точная команда запуска
службы обновления.

Проверка на сервере:

```bash
sudo visudo -cf /etc/sudoers.d/crop-forecast-bot-deploy
sudo cat /var/lib/crop-forecast-deploy/.ssh/authorized_keys
sudo systemctl status crop-forecast-bot-update.timer
```

### 4.3. Зафиксировать ключ сервера

На доверенной машине получите ключ узла:

```bash
ssh-keyscan -H -p 22 example.org
```

Сверьте его отпечаток с выводом, полученным через консоль сервера:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Не сохраняйте результат `ssh-keyscan` без независимой сверки отпечатка.

### 4.4. Настроить защищённое окружение GitHub

В репозитории создайте окружение `production`.

Добавьте в него секреты:

| Имя | Значение |
|---|---|
| `DEPLOY_HOST` | имя или адрес сервера |
| `DEPLOY_PORT` | порт SSH, обычно `22` |
| `DEPLOY_USER` | `cropdeploy` |
| `DEPLOY_SSH_KEY` | содержимое закрытого ключа |
| `DEPLOY_KNOWN_HOSTS` | проверенная строка `known_hosts` |

Добавьте переменную окружения:

```text
DEPLOY_TRIGGER_ENABLED=true
```

Пока переменная отсутствует или не равна `true`, процесс немедленного
развёртывания пропускается и не создаёт ошибок. Базовый таймер продолжает
работать.

### 4.5. Последовательность после настройки

```text
коммит или слияние в main
→ CI проверяет точный коммит
→ при успехе GitHub подключается ограниченным ключом
→ systemd запускает update.sh
→ update.sh повторно проверяет, что актуальный main зелёный
→ создаёт выпуск и выполняет миграции
→ переключает символьную ссылку
→ перезапускает бот
→ проверяет heartbeat
→ при ошибке возвращает предыдущий выпуск
```

Если GitHub не может подключиться к серверу, процесс в GitHub будет отмечен
ошибкой, но таймер на сервере повторит обновление самостоятельно.

## 5. Диагностика лишних сообщений

Проверить число фактических запусков:

```bash
sudo journalctl -u crop-forecast-bot.service \
  --since today \
  | grep 'Ensemble weather-risk screening started'
```

Проверить перезапуски:

```bash
sudo journalctl -u crop-forecast-bot.service \
  --since today \
  | grep -E 'Started|Stopping|Telegram API verified'
```

Проверить историю обновлений:

```bash
sudo journalctl -u crop-forecast-bot-update.service \
  --since today
```

Проверить состояние снимков PostgreSQL:

```sql
SELECT
    field_id,
    model,
    state_version,
    state_json,
    last_observed_at,
    last_notified_at
FROM risk_delivery_states
ORDER BY field_id;
```

После первого обновления с новой схемой текущий активный период может быть
отправлен один раз, потому что прежняя версия не хранила семантический снимок.
Дальнейшие одинаковые перерасчёты повторов не создают.

## 6. Критерии приёмки

- один период жары при четырёх перерасчётах в сутки создаёт одно сообщение;
- изменение только доли ансамбля не создаёт сообщение;
- продление или сокращение периода создаёт одно понятное уточнение;
- полное снятие будущего периода создаёт одно сообщение;
- следующий идентичный перерасчёт после снятия молчит;
- перезапуск процесса не сбрасывает состояние;
- тихие часы откладывают обычное уточнение;
- существенно изменившийся высокий риск может обойти тихие часы;
- обновление запускается только после успешной проверки `main`;
- отсутствие GitHub-сигнала компенсируется системным таймером;
- ошибка миграции или проверки работоспособности приводит к откату выпуска.
