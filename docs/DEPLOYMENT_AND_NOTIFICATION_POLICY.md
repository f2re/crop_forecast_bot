# Автообновление и политика погодных уведомлений

Дата аудита: **2026-08-03**.

## 1. Вывод аудита

### Развёртывание

В проекте используется безопасное автоматическое обновление целевой системы:

```text
systemd-таймер
→ scripts/update.sh
→ проверка точного коммита main в GitHub Actions
→ новый изолированный выпуск
→ миграции
→ предварительная проверка
→ атомарное переключение
→ проверка работоспособности
→ автоматический откат при ошибке
```

Таймер `crop-forecast-bot-update.timer` проверяет `main` каждые 15 минут. Это
основной путь: серверу не нужен входящий HTTP-перехватчик, отдельный агент или
открытый служебный порт.

Для немедленного запуска после успешного CI используется необязательный процесс
`.github/workflows/deploy-production.yml`. Он подключается отдельным ограниченным
SSH-ключом и запускает тот же `crop-forecast-bot-update.service`. Проверка SHA,
миграции, переключение выпуска, контроль heartbeat и откат остаются на сервере.

### Уведомления

Погодный расчёт выполняется около 00:10, 06:10, 12:10 и 18:10 по часовому поясу
планировщика. Дополнительно возможна одна проверка после здорового запуска бота.
Частота расчёта не должна совпадать с частотой сообщений: новый прогнозный запуск
сам по себе не является причиной уведомления.

Старая защита учитывала отдельную дату и ступень доли ансамбля. Поэтому один
период жары мог получать новый технический отпечаток после небольшого изменения
числа членов ансамбля. Теперь защита работает после объединения соседних суток в
смысловой период.

## 2. Смысловая модель погодного события

Один непрерывный период определяется только существенными признаками:

```text
тип явления
+ дата начала
+ дата окончания
+ наивысший уровень
```

Повторное сообщение отправляется, когда:

1. появился новый будущий период;
2. период начнётся раньше или позже;
3. период закончится раньше или продлится;
4. изменился уровень;
5. период разделился на части или несколько частей объединились;
6. ранее ожидавшееся будущее явление больше не подтверждается.

Не считаются новым событием:

- изменение доли ансамбля без смены уровня;
- изменение медианы, P10, P90 или числа валидных членов;
- очередной запуск модели с прежними границами периода;
- естественное завершение уже прошедшего календарного дня;
- перезапуск бота;
- потеря краткосрочного Redis-ключа при сохранённом состоянии PostgreSQL.

Последний принятый снимок хранится в `risk_delivery_states`. Redis используется
для защиты внешнего Telegram-вызова и суточного ограничения.

### 2.1. Два разных Redis-ключа

Для режима «одна сводка в сутки» используются два независимых ключа:

```text
transition:<hash>
```

означает: конкретное изменение прогноза уже доставлено;

```text
daily:<локальная дата>
```

означает: обычная суточная сводка сегодня уже отправлена.

Эти понятия нельзя объединять в один ключ. Разделение устраняет две
противоположные ошибки:

- после отправки Telegram и аварии до записи PostgreSQL тот же переход
  распознаётся как уже доставленный и не повторяется на следующий день;
- другое существенное изменение в те же сутки блокируется только суточным
  лимитом, но остаётся ожидающим и попадёт в следующую сводку.

Если Telegram-вызов завершился ошибкой, обе короткие резервации снимаются и
переход можно повторить. Если суточный лимит уже занят, резервация нового
перехода также снимается, чтобы он не считался доставленным.

### 2.2. Все периоды сохраняются

Ограничение `max_events=5` относится к пяти типам погодного риска, а не к первым
пяти отдельным периодам. Например, шесть раздельных эпизодов жары одного типа не
обрезаются до пяти и не поглощаются состоянием без сообщения.

Если лимит типов когда-либо уменьшится, недоставленные типы остаются в предыдущем
PostgreSQL-снимке и будут обработаны последующим запуском.

### 2.3. Повторные карточки одного поля

Несколько карточек одного пользователя с координатами, совпадающими до пяти
знаков после запятой, и одинаковыми настройками доставки автоматически
объединяются в один погодный объект. В сообщении сохраняются все названия полей и
все культуры этой точки.

Карточки с разными режимами доставки или тихими часами не объединяются: это
считается явным пользовательским решением. Ежедневные агроотчёты также остаются
раздельными, поскольку они зависят от культуры и сезона.

### 2.4. Примеры

Первое сообщение:

```text
Жара ожидается 5–9 августа.
```

Следующие расчёты с тем же периодом молчат, даже если согласованность ансамбля
изменилась с 55 до 72 процентов.

Уточнение:

```text
Жара продлится дольше: до 11 августа вместо 9 августа.
```

Снятие:

```text
Ранее ожидавшийся период жары 5–9 августа больше не подтверждается.
```

## 3. Базовое автообновление таймером

Первичная установка:

```bash
git clone https://github.com/f2re/crop_forecast_bot.git
cd crop_forecast_bot
sudo bash scripts/deploy.sh
```

Проверка:

```bash
systemctl status crop-forecast-bot.service --no-pager
systemctl status crop-forecast-bot-update.timer --no-pager
systemctl list-timers crop-forecast-bot-update.timer
sudo journalctl -u crop-forecast-bot-update.service -n 200 --no-pager
```

Ручной запуск той же безопасной процедуры:

```bash
sudo systemctl start crop-forecast-bot-update.service
sudo journalctl -u crop-forecast-bot-update.service -f
```

Не заменяйте её на `git pull` в рабочем каталоге: такой запуск не обеспечивает
атомарность, проверку миграций, контроль процесса и автоматический откат.

## 4. Немедленный GitHub-сигнал

Таймер должен оставаться включённым как резерв.

### 4.1. Создать отдельный ключ

```bash
ssh-keygen \
  -t ed25519 \
  -f cropbot_github_deploy \
  -C crop-forecast-bot-github-deploy
chmod 600 cropbot_github_deploy
```

Закрытый ключ хранится только в GitHub Environment. Открытый устанавливается на
сервер.

### 4.2. Установить ограниченный обработчик на сервере

```bash
sudo bash scripts/install-github-deploy-trigger.sh \
  /путь/cropbot_github_deploy.pub
```

Скрипт создаёт пользователя `cropdeploy`. Ключ может выполнить только:

```text
systemctl --no-block start crop-forecast-bot-update.service
```

Произвольная оболочка, псевдотерминал, перенаправление портов и SSH-agent
запрещены.

Проверка:

```bash
sudo visudo -cf /etc/sudoers.d/crop-forecast-bot-deploy
sudo cat /var/lib/crop-forecast-deploy/.ssh/authorized_keys
sudo systemctl status crop-forecast-bot-update.timer --no-pager
```

### 4.3. Зафиксировать ключ узла

```bash
ssh-keyscan -H -p 22 example.org > cropbot_known_hosts
```

Перед использованием независимо сравните отпечаток через консоль сервера:

```bash
sudo ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

### 4.4. Автоматически настроить GitHub

На административной машине установите GitHub CLI и выполните `gh auth login`.
Затем:

```bash
REPOSITORY=f2re/crop_forecast_bot \
DEPLOY_HOST=example.org \
DEPLOY_PORT=22 \
DEPLOY_USER=cropdeploy \
DEPLOY_SSH_KEY_FILE="$PWD/cropbot_github_deploy" \
DEPLOY_KNOWN_HOSTS_FILE="$PWD/cropbot_known_hosts" \
RUN_TRIGGER_TEST=true \
bash scripts/configure-github-deploy.sh
```

Скрипт работает в Linux и macOS и выполняет:

1. проверку GitHub CLI и авторизации;
2. проверку режима закрытого ключа `0400` или `0600`;
3. создание или обновление окружения `production`;
4. запись `DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_USER`, `DEPLOY_SSH_KEY` и
   `DEPLOY_KNOWN_HOSTS` как секретов окружения;
5. запись `DEPLOY_TRIGGER_ENABLED=true` как переменной репозитория;
6. проверку наличия всех настроек без вывода значений секретов;
7. при `RUN_TRIGGER_TEST=true` — ручной запуск процесса проверки.

Флаг должен находиться на уровне репозитория: условие задания вычисляется до
запуска runner. Секреты остаются в защищённом окружении `production`.

### 4.5. Ручная проверка GitHub-триггера

Workflow поддерживает `workflow_dispatch`:

```bash
gh workflow run deploy-production.yml \
  --repo f2re/crop_forecast_bot \
  --ref main
```

Он выполняет тот же ограниченный SSH-сигнал. После проверки:

```bash
gh run list \
  --repo f2re/crop_forecast_bot \
  --workflow deploy-production.yml \
  --limit 5
```

Если GitHub не может подключиться, серверный таймер всё равно выполнит обновление
позже.

## 5. Диагностика уведомлений

Число фактических расчётов:

```bash
sudo journalctl -u crop-forecast-bot.service \
  --since today \
  | grep 'Ensemble weather-risk screening started'
```

Перезапуски:

```bash
sudo journalctl -u crop-forecast-bot.service \
  --since today \
  | grep -E 'Started|Stopping|Telegram API verified'
```

Обновления:

```bash
sudo journalctl -u crop-forecast-bot-update.service --since today
```

Состояния периодов:

```sql
SELECT
    field_id,
    model,
    delivery_mode,
    state_version,
    state_json,
    last_observed_at,
    last_notified_at
FROM risk_delivery_states
ORDER BY field_id;
```

Состояния отдельных сигналов:

```sql
SELECT
    r.field_id,
    s.risk_type,
    s.event_date,
    s.delivery_state,
    s.notified_at
FROM risk_forecast_signals AS s
JOIN risk_forecast_runs AS r ON r.id = s.run_id
ORDER BY r.retrieved_at DESC, r.field_id, s.event_date
LIMIT 100;
```

`delivery_state='deferred'` означает, что изменение было корректно отложено
суточным лимитом, а не потеряно.

Повторные координаты:

```sql
SELECT
    u.telegram_id,
    round(f.latitude::numeric, 5) AS latitude_key,
    round(f.longitude::numeric, 5) AS longitude_key,
    array_agg(f.id ORDER BY f.id) AS field_ids,
    array_agg(f.name ORDER BY f.id) AS field_names
FROM fields AS f
JOIN users AS u ON u.id = f.user_id
WHERE f.frost_alerts_enabled IS TRUE
GROUP BY
    u.telegram_id,
    round(f.latitude::numeric, 5),
    round(f.longitude::numeric, 5)
HAVING count(*) > 1
ORDER BY u.telegram_id, latitude_key, longitude_key;
```

Такие записи больше не создают повторные погодные сообщения при одинаковых
настройках доставки, но их полезно привести в порядок в интерфейсе полей.

После первой установки миграции `20260803_0008` текущий активный период может
прийти один раз, поскольку прежняя версия не имела постоянного смыслового
снимка.

## 6. Критерии приёмки

- один период жары при четырёх расчётах в сутки создаёт одно сообщение;
- изменение только доли ансамбля не создаёт сообщение;
- продление или сокращение периода создаёт одно понятное уточнение;
- полное снятие будущего периода создаёт одно сообщение;
- повтор того же перехода после сбоя Telegram/PostgreSQL не отправляется;
- другое изменение в те же сутки остаётся ожидающим;
- ожидающее изменение отправляется в следующие локальные сутки;
- все раздельные периоды одного типа сохраняются;
- недоставленный тип риска не поглощается новым снимком;
- дубликаты одной геоточки с одинаковой политикой дают одно сообщение;
- тихие часы откладывают обычное уточнение;
- существенно изменившийся высокий риск может обойти тихие часы;
- обновление запускается только после успешной проверки `main`;
- GitHub-настройка воспроизводится одним проверяемым скриптом;
- GitHub-триггер можно проверить вручную;
- отсутствие GitHub-сигнала компенсируется системным таймером;
- ошибка миграции или проверки работоспособности приводит к откату выпуска.
