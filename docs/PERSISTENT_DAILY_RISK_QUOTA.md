# Постоянный суточный лимит погодных уведомлений

Дата актуализации: **2026-08-03**.

## Назначение

Режим `digest` должен отправлять не более одной обычной сводки погодных рисков за
локальные сутки поля. Redis-ключ ускоряет проверку и защищает от параллельных
запусков, но не является единственным источником истины: Redis может быть
перезапущен, очищен или не сохранить продлённый TTL.

Поэтому суточный лимит подтверждается двумя независимыми уровнями:

```text
Redis daily:<local-date>
+
PostgreSQL risk_delivery_states.last_notified_at
```

## Локальная дата

`last_notified_at` хранится в PostgreSQL как UTC `DateTime`. Старые записи без
информации о часовом поясе трактуются как UTC. Перед сравнением значение
переводится в `ZoneInfo` поля.

Пример:

```text
last_notified_at: 2026-08-03 22:30 UTC
поле: Europe/Moscow
локальное время уведомления: 2026-08-04 01:30
```

Такое сообщение относится к 4 августа, а не к 3 августа.

Переходы летнего времени проверяются по календарной дате, поэтому оба варианта
повторяющегося локального часа относятся к одним суткам.

## Алгоритм

1. Принятый запуск ансамбля сохраняется в истории.
2. Текущие периоды сравниваются с последним доставленным снимком.
3. Если существенных изменений нет, сообщение не формируется.
4. Для обычного `digest` проверяется `last_notified_at` в локальном времени поля.
5. Если обычное сообщение уже было сегодня:
   - Telegram не вызывается;
   - Redis-резервация перехода не создаётся;
   - новый снимок не принимается как доставленный;
   - отдельные сигналы получают состояние `deferred`;
   - уточнение остаётся ожидающим до следующих локальных суток.
6. Если постоянный лимит свободен, дополнительно применяются transition- и
   daily-ключи Redis.
7. После успешной отправки PostgreSQL получает новый снимок и UTC-время
   уведомления.

## Восстановление после аварии

Возможен порядок:

```text
Telegram принял сообщение
→ transition-ключ Redis сохранён
→ процесс завершился до записи PostgreSQL
```

При следующем запуске transition-ключ возвращает `already_delivered`. Бот не
повторяет Telegram-вызов, но восстанавливает:

- смысловой снимок периодов;
- `last_notified_at`;
- постоянный суточный лимит.

## Высокий приоритет

Существенно изменившийся высокий риск может быть отправлен немедленно, даже если
обычный digest уже был в эти сутки. После принятия такого сообщения
`last_notified_at` обновляется, поэтому последующее обычное уточнение остаётся до
следующих суток.

Это исключение относится только к изменению высокого уровня. Повтор того же
высокого перехода блокируется transition-ключом.

## Диагностика

Проверить постоянное состояние:

```sql
SELECT
    field_id,
    model,
    delivery_mode,
    state_json,
    last_observed_at,
    last_notified_at
FROM risk_delivery_states
ORDER BY field_id;
```

Проверить отложенные сигналы:

```sql
SELECT
    r.field_id,
    r.retrieved_at,
    s.risk_type,
    s.event_date,
    s.delivery_state,
    s.notified_at
FROM risk_forecast_signals AS s
JOIN risk_forecast_runs AS r ON r.id = s.run_id
WHERE s.delivery_state = 'deferred'
ORDER BY r.retrieved_at DESC, r.field_id, s.event_date;
```

Проверить журнал:

```bash
sudo journalctl -u crop-forecast-bot.service --since today | \
  grep -E 'durable local-day quota|retained for the next local day'
```

## Критерии приёмки

- потеря всех краткосрочных Redis-ключей не создаёт второй обычный digest в те же
  локальные сутки;
- UTC-время корректно переводится в часовой пояс поля;
- DST fold не создаёт две календарные даты;
- отложенное изменение не меняет доставленный снимок;
- на следующие локальные сутки изменение снова доступно для отправки;
- восстановление по transition-ключу не вызывает Telegram повторно;
- высокий приоритет сохраняет отдельный немедленный путь.
